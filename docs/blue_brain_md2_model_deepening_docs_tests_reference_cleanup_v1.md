## 2) Operative model surface that remains canonical

The maintained model-deepened surface is exactly:

- relation: `Amygdala ↔ Thalamus`,
- level: relation-level only,
- current mode: bounded Kuramoto-like current mode,
- role: advisory-only / diagnostic bounded support,
- leverage: coupling, synchrony, gating, and timing modulation only,
- contract anchor: existing IR1 relation contracts and region contracts remain leading,
- maintenance status: frozen semantics; cleanup, tests, and docs alignment only.

Everything else remains outside the canonical first-deepening surface. `Amygdala ↔ Basal Ganglia` is deferred and not opened in MD2. HH-like paths stay simulation-only/diagnostic-only or later-selective ideas that require explicit re-scope before any implementation.

## 3) Diagnostics, contract, and consumer-read semantics

The following distinctions are the maintenance-facing contract and must not drift:

- model state is not contract state,
- model state is not region authority,
- diagnostic model output is not operational authority,
- `diagnostic-only` has no advisory support,
- `caveated advisory-only` is not strong operational support,
- `deferred`, `blocked`, and `insufficient` are no-support states,
- `non-canonical/internal-only` has no canonical Runtime, Selection, Reference, or Execution consumer read,
- canonical `Amygdala ↔ Thalamus` reads use the bounded advisory/diagnostic consumer-read class only.

The canonical support classes remain those exposed by `BlueBrainMd1FirstDeepeningContractSupportClass`; documentation must not reinterpret diagnostic or caveated model output as stronger authority than the code returns.

## 4) Guard, freeze, and boundary hints that must stay visible

MD2 keeps the existing no-direct-* guard line visible:

- no direct action trigger,
- no direct execution trigger,
- no direct retry trigger or retry orchestration,
- no direct memory commit and no implicit memory persistence,
- no direct compute invocation and no Compute-Core expansion,
- no policy/governance authority,
- no safety override,
- no planner/agent platform,
- no retrieval/consolidation/reasoning platform,
- no implicit second model-deepening candidate,
- no global Kuramoto, HH, or general model platform.

Further model-deepening candidates require explicit re-scope after this first maintenance surface remains stable.

## 5) Cleanup and legacy handling

MD1 decision, implementation, hardening, and closure docs remain supporting references. They are not competing current authority for MD2 maintenance. If wording in older docs appears broader than the code surface, maintainers must read it through this MD2 reference map and the MD2 Prompt 1 stabilization line.

Deprecated, residual, or legacy model references must be handled in one of two ways:

1. point back to this canonical MD2 maintenance reference map, or
2. explicitly mark the path as non-canonical/internal-only with no consumer read, no contract support, and no operational authority.

Do not leave aspirational language that implies a second active deepening candidate, a productive HH lane, direct action/execution/retry/memory/compute authority, or a global model platform.

The targeted maintenance test surface should keep these checks explicit and small:
